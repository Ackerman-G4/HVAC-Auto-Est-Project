1. Executive Summary 
This plan is the successor to the v3.0 Security-Hardened plan. Most of v3.0 has now shipped: the birthday 
login is deleted, the real equipment catalog is wired in, price overrides are admin-gated and audited, BOQ 
snapshots are hash-locked, the admin portal exists with five live tabs, per-user project ownership is enforced, 
lockout and password policy are live, and — as of Wave 6 — price overrides actually flow into quoted prices, 
login lockout is IP-aware, and the OpenFOAM export path produces structurally valid solver cases with a 
containerized Cloud Run solver written and unit-checked. 
What remains is the part v3.0 sketched most ambitiously and least concretely: the CFD engine, the 3D view, 
and the interface that presents them. This document replaces v3.0’s Section 8 (CFD & 3D) and Section 5 (UI) 
with a design that is grounded in the code that actually exists, corrects three of v3.0’s technology choices that 
would have cost months for negative return, and defines the exact sequence to a system you can put in front 
of a paying client. 
How to read this document 
Sections 2 and 3 are decisions and rationale — read them once, then hold the rest of the plan accountable to 
them. Sections 4–7 are the build plans (CFD, 3D, UI, remaining engine work). Section 8 is the stack. Section 9 is 
the timeline sized for one developer. Section 10 is the validation gate that separates "it runs" from 
"engineering-grade."

2. Guiding Engineering Decisions 
These five decisions shape everything else in the plan. Each one is stated with its reasoning so it can be 
challenged on the merits later — a decision you can’t interrogate is a superstition, not engineering. 
D1 — OpenFOAM is the engineering-grade solver. Do not build a custom SST k-ω. 
v3.0 called for a from-scratch Python solver with SST k-ω turbulence, octree adaptive mesh refinement, and 
conjugate heat transfer, JIT-compiled with Numba. Each of those is individually a serious project; together 
they are a research codebase. Worse, a custom solver has no validation pedigree — when a client’s 
mechanical engineer asks "what solver produced this," the answer "one I wrote myself" ends the 
conversation, while "OpenFOAM, the same platform used across the HVAC and automotive industries" starts 
one. 
The decisive detail: the exporter built in Wave 6 already maps the turbulence model selection to OpenFOAM 
— including k-omega-sst → kOmegaSST. SST k-ω, the headline feature of v3.0’s custom-solver plan, is a 
dropdown option on the OpenFOAM path once that path is validated. You get v3.0’s accuracy goal with zero 
solver-development effort. 
– Keep the existing TypeScript SIMPLE/k-ε in-browser solver as the free Preview tier. It runs instantly, costs 
nothing, and is the only path with humidity transport — a genuine advantage in Philippine 
psychrometrics. 
– OpenFOAM (buoyantSimpleFoam, later kOmegaSST) is the paid Engineering tier: slower, costs compute, 
produces defensible numbers. 
===== PAGE 5 =====
– Every simulation result is permanently labeled with its solver tier. Never let a Preview number appear 
where an Engineering number is expected. 
D2 — The tier split is a product feature, not a compromise 
Preview vs. Engineering maps directly onto the SaaS pricing tiers already planned in the commercial layer: 
free users iterate quickly with Preview; paying users unlock Engineering runs. The same geometry, cases, and 
3D viewer serve both — only the solver behind the run changes. This is why the SimulationResult/RunJob 
contract must stay solver-agnostic, which the existing runSource field (internal | openfoam | simflow | 
manual-import) already supports. 
D3 — No Rust/WASM until profiling demands it 
The geometry pipeline (parseRoomPolygon → extrudeRoomFromPolygon → detectAdjacentRooms → 
buildBuildingGeometryFromFloors) is working TypeScript operating on tens of rooms with tens of vertices 
each. That is microseconds of work. A Rust/WASM rewrite adds a toolchain, a build step, a language, and an 
FFI boundary to a part of the system that has never appeared in a performance trace. Rule: no rewrite 
without a profile showing the extruder above 10% of frame or request time. 
D4 — WebGL2 now, WebGPU as progressive enhancement later 
Volumetric temperature rendering at 25k–500k cells is comfortably within WebGL2 raymarching capability, 
and WebGL2 works on effectively every device a Philippine contractor’s office owns. WebGPU support is still 
uneven on the long tail of hardware. Three.js abstracts the difference: written correctly, the R3F viewer can 
adopt the WebGPURenderer later with minimal component changes. Ship compatibility first, adopt the faster 
renderer when it’s free to do so. 
D5 — No new queue infrastructure 
Cloud Run Jobs is the compute queue; the runJobs subcollection in Firestore (already built, with status, 
residuals, snapshots, and rules) is the job state. BullMQ+Redis would duplicate both while adding a paid 
dependency and another security surface. The per-user rate limiting v3.0 wanted from BullMQ is already 
implemented at the API layer (evaluateRateLimit) and can be extended per-route without any new 
infrastructure.

4. CFD Engine — From Scaffold to Engineering-Grade 
The Wave 6/7 work established the skeleton. This section is the full build-out, restated as one coherent 
program with its verification gates. Nothing here is speculative infrastructure: every named store function, 
type, and file already exists in the repository unless marked NEW. 
4.1 Phase C1 — Prove the solver locally (gate: one real room solves end-to-end) 
– Build the cfd-solver image locally. The Dockerfile’s install method (dl.openfoam.com apt repo, 
openfoam2406-default, /usr/lib/openfoam/openfoam2406) was verified against openfoam.com’s current 
documentation in July 2026. 
– Export one small real room (one inlet, one outlet, no obstructions) via a temporary debug script calling 
buildOpenFOAMConfig + generateCaseFiles, and run the container with plain volume mounts — no GCS, 
no callback. 
– Expected first-run failure modes, in order of likelihood: degenerate boundary faces on unusual aspect 
ratios (read checkMesh output — the wrapper runs it non-fatally for exactly this reason); empty topoSet 
faceSets if a patch’s cells don’t touch a true outer face; divergence before the first write interval (relax 
fvSolution under-relaxation factors); fluidfoam shape mismatch (add an assertion comparing 
readmesh(structured=True) shape to nx/ny/nz before trusting any field). 
– Gate to pass: output JSON contains non-NaN, physically plausible temperature/velocity/pressure arrays 
for that room. 
4.2 Phase C2 — Cloud infrastructure 
– Artifact Registry repo; push the proven image. 
– GCS exchange bucket with a lifecycle rule deleting objects after ~7 days — job inputs/outputs are 
transient.

– gcloud run jobs create cfd-solver --cpu 4 --memory 8Gi --task-timeout 3600 --max-retries 0; tune after

4.5 Phase C5 — Real geometry (snappyHexMesh) 
===== PAGE 8 =====
Only after C1–C4: obstruction-aware meshing for furniture, racks, and interior walls. The voxel zones array in 
geometry-builder.ts already knows which cells are solid; the new work is a voxel→STL export (box-per-solid-
cell is sufficient at these resolutions), a snappyHexMeshDict generator targeting that STL, and a branch in 
run_solve.py’s mesh pipeline when solid zones are present. Treat as its own effort with its own validation 
pass — a meaningfully different meshing path deserves its own gate. 
4.6 Explicit non-goals for the CFD engine in v2.0 
– No humidity field on the OpenFOAM path (would require adding a scalar transport equation to the case 
setup; the Preview tier covers psychrometric questions until then). The result importer’s humidity field 
stays optional for exactly this reason. 
– No transient (time-accurate) simulation — steady RANS answers the design questions a BOQ needs. 
– No conjugate heat transfer through walls — wall boundary conditions with fixed T / heat flux are the 
correct fidelity for room-level design. 
5. 3D Visualization — React Three Fiber Overhaul 
The current viewer (raw Three.js in BuildingSimulationViewer3D + CFDOverlay3D, ~1,150 lines) works and 
renders real geometry — the v3.0 audit line "no real geometry" is no longer true and was re-verified during 
Wave 6. What raw Three.js costs is composability: every layer (volume, vectors, particles, hotspots) is hand-
managed imperative code. React Three Fiber makes each layer a component with props, which is what lets 
the viewer grow the v2.0 feature set without collapsing. 
5.1 Migration strategy — strangler, not rewrite 
– New R3F <SimulationCanvas> mounts alongside the old viewer behind a UI toggle. Old viewer is deleted 
only after the new one reaches feature parity (checklist: geometry, temperature overlay, velocity display, 
hotspots, camera controls, mobile touch). 
– Dependencies: @react-three/fiber, @react-three/drei (already on three ~r128-compatible APIs in the 
repo — pin R3F/drei versions to the three version npm resolves, and note OrbitControls comes from drei, 
sidestepping the r128 OrbitControls gap noted in the codebase). 
– Component tree: <SimulationCanvas> → <BuildingShell> (extruded rooms, wall thickness by construction 
type) → <TemperatureVolume> → <VelocityGlyphs> → <SupplyAirParticles> → <HotspotMarkers> → 
<SectionPlane> → <ComfortOverlay>. Each takes the RunFieldSnapshot data as props and nothing else — 
solver-agnostic by construction.

5.3 Performance budgets (hard limits, checked in review) 
– 60 fps on a mid-range laptop iGPU for a 35k-cell room with volume + glyphs + 4k particles; 30 fps floor on 
a 2022-class Android tablet. 
– Draw calls < 100 in the full-feature view; volume raymarch ≤ 128 steps; particle count adaptive (halve 
until frame budget met). 
– LOD: > 30 m camera distance → room boxes only; 10–30 m → walls, no volume; < 10 m → everything. 
(Retains v3.0’s LOD concept unchanged — it was correct.) 
– All layers respect prefers-reduced-motion: particles pause, animations become fades. 
6. UI & Animation System 
v3.0’s design tokens were good and are retained unchanged (jade accent, ink primary, copper for cost, 
destructive red, the light/dark pairs). v2.0 adds the motion system, the CFD-specific surfaces, and the rules 
that keep animation from becoming decoration. 
6.1 Motion principles 
– Library: Framer Motion (motion/react) for DOM; R3F’s own frame loop for 3D. One motion vocabulary: 
durations 150ms (micro), 250ms (panel), 400ms (page); easing cubic-bezier(0.2, 0, 0, 1); nothing bounces 
in an engineering tool. 
– Motion must encode meaning: state change, causality, or spatial continuity. If removing an animation 
loses no information, remove it. 
– prefers-reduced-motion collapses everything to opacity fades. This is an accessibility requirement, not a 
preference. 
– Numbers animate by counting (BOQ totals, TR values) only on first computation — re-renders show final 
values instantly. Copper color reserved for currency figures, as in v3.0.

10. Testing, Verification & Quality Gates 
– Every phase ends with: npx tsc --noEmit clean, eslint clean, and its smoke script green. The Wave 6 
pattern (scripts/ts/smoke-price-override.ts registered as an npm script) is the template — cheap, 
behavioral, honest. 
– New smoke scripts to add as phases land: smoke-openfoam-export (case-file structural checks — the 
Wave 6 version of this proved its worth by catching a real patch-name mismatch before it ever reached a 
solver), smoke-boq-sections (11 sections present, totals reconcile), smoke-validation-ladder (replays V1–
V4 checks against a stored reference result). 
– Adopt vitest for pure-function unit tests (pricing resolution, BOQ math, geometry helpers) — the 
codebase currently has zero test framework; the smoke scripts filled that gap tactically, vitest fills it 
structurally. 
– CI: on PR — typecheck + lint + unit + smokes; nightly — cfd-solver image build (catches upstream 
OpenFOAM repo changes early). 
– The validation log from Section 4.4 is a permanent artifact. Version it in the repo (docs/validation-
log.md). It is the difference between marketing language and an engineering claim.

12. Professional Assessment 
The v3.0 document’s core judgment — treat this as money-adjacent software — was right, and the platform 
now embodies it: audited prices, hash-locked BOQs, enforced ownership, real lockouts. Its weakness was that 
its most ambitious sections (custom SST k-ω solver, Rust geometry, WebGPU, Redis queues) specified 
impressive technology rather than a reachable path, and for a solo developer those two things are opposites. 
v2.0’s bet is different: spend your innovation budget where clients can see it (the viewer, the comfort overlay, 
the load-breakdown story) and where correctness is provable (the validation ladder), and rent everything else 
from tools with decades of validation behind them. OpenFOAM gives you v3.0’s turbulence-model ambition 
as a configuration option. React Three Fiber gives you a viewer that can grow. The tier system turns the solver 
split into pricing structure instead of technical debt. 
One caution worth keeping in writing: nothing in this plan is "engineering-grade" until Section 4.4’s ladder 
passes and its log exists. Hold every future version of this document — and every demo you give — to that 
standard. It is the habit that will separate this product from every other estimation tool in the market it 
enters.
